## RPC decision

- `configure_top_two_group_playoff_revisioned`: reused by the existing setup route for explicit playoff configuration; finalize does not call it because stage configuration is already supplied by the stage plan.
- `finalize_tournament_draw`: reused inside the new wrapper as the atomic stage writer. It persists `group_label` and `seed_in_stage` in `tournament_stage_entrants` and creates fixtures in the same transaction.
- `gh_save_draw`: not used; it would create a parallel draw write path and is not the locked multi-stage finalize contract.
- `confirm_tournament_pairs_revisioned`: not used; pair confirmation belongs to T1.C / existing pairing flow and finalize must consume stable pairs.
- `guard_locked_division_setup_write`: not called directly; the finalize RPC locks stage rows and rejects existing/played fixture state. Existing guarded setup mutations remain in the setup route.
- `unlock_tournament_draw`: not used; unlock is an explicit separate recovery operation and must not be part of finalize.
- `unseed_division_group_playoff`: not used; it is an explicit repair action already exposed by setup and must not run implicitly.

## API behavior

`POST /api/tournament-v2/setup/finalize` requires admin session, validates tournament/division/revision/idempotency/draw/stage plan, and invokes `finalize_unified_setup_v2` with server-derived `group_id`. The wrapper validates every stage belongs to the same tenant/tournament/division, then delegates all stage writes in one database transaction. Draw assignments are represented through the existing RPC's `tournament_stage_entrants(group_label, seed_in_stage)` path; no draw-slot table is created or referenced.

The response redirects to schedule and does not set LIVE. Errors use the frozen `{ error: { code, message } }` envelope. RPC failures map to stable setup codes.
